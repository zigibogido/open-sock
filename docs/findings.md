## USENIX WOOT'24 Eufy paper (Goeman et al.) - transferable crypto findings
Paper: https://www.usenix.org/system/files/woot24-goeman.pdf (local copy: work/papers/woot24-goeman.txt, pdftotext -layout). Paper covers Eufy **doorbell + Homebase** (MIPS firmware), not the sock/BLE directly, but shares the same binary names/SDK (`home_security`, `PPCS_ID`) found in our APK, so the key-derivation weaknesses are a strong lead, not yet confirmed to apply to this app/device.
- **WPA2-PSK derivation (CVE-2023-37822)**: `WPA2-PSK = B64(MD5(serial))[0:7]` (8 chars from base64 of the MD5 of the device serial). Only ~24 bits of real entropy once the vulnerable shortened-MD5 step is used; serial is learnable from device casing, LAN/WAN traffic, or brute force.
  - Serial number format: `AAAAAAA` (device-type, e.g. T8010) + 1 char batch id (P/N, 0-3) + 7 hex chars (device-specific).
- **P2P/media AES key derivation**: AES-ECB (weak mode) used throughout. Media key = `SHA256("01"+baseCode+seed)` then a custom "Obfuscate2" byte transform; `baseCode = serial[0:l] + getPPCSSuffix(PPCS_ID)`; `seed = Obfuscate1(MD5("01"+random+str(1000-sfx)))`. `getPPCSSuffix` sums 4 digits from the middle segment of PPCS_ID (doubles if <5) → only 480 possible values, brute-forceable.
  - PPCS_ID format: `AAAAAAA-000000-BBBBB` (20 chars, 3 dash-separated parts), interceptable from App<->Homebase network traffic.
  - All of this lives in the device's own `home_security` MIPS binary (on the Homebase/base, not the phone) — recovered via symbolic execution (dAngr, open-sourced by the authors) because Ghidra's MIPS decompilation was unreliable.
- **No BLE-specific findings in this paper** — their BLE reference is to an unrelated Xiaomi case study, not Eufy. Eufy's own BLE local protocol (what we're after for the sock) is not documented here.

## MAJOR FIND: AES key logged in cleartext via logcat (2026-11-20, Mi 9T rooted device)

  HomeSecurity: ------>>[int_aes_encryptkey] aes test password=524071D-333113-M ret=0

## BREAKTHROUGH: Sock telemetry decrypted — full protocol cracked (2026-11-20)
**This is the answer for sock functionality.** The P2P/PPCS UDP channel (not BLE) carries the sock's live data, and it decrypts cleanly.

### Capture setup
- `tcpdump -i wlan0 -w capture.pcap host 192.168.7.3` on the rooted Mi 9T (no port filter — P2P uses ephemeral UDP ports, not the earlier nmap-found TCP ports 32290 etc., which are unrelated/irrelevant).
- Protocol is **PPCS** (matches `libNDT_API_PPCS.so`), magic byte `0xf1`: `f1 e0 00 00`=ping (phone->base), `f1 e1 00 00`=pong (base->phone), `f1 d0 <len_LE16> ...`=data packet, `f1 d1 ...`=ack.

### Decryption
- **Key:** first 16 bytes of the literal ASCII string logged by `HomeSecurity`/`leo_p2p` (`524071D-333113-M`, i.e. drop the trailing `-M`): `35 32 34 30 37 31 44 2d 33 33 33 31 31 33 2d` hex, or ASCII `524071D-333113-`.
- **Cipher: AES-128-ECB**, no IV, raw ASCII bytes used directly as the key (no hashing/KDF) — matches the WOOT paper's finding that Eufy uses weak/custom crypto and AES-ECB broadly.
- **Packet layout**: `f1 d0 <len_LE16>` (4 bytes) + 20-byte sub-header (`d1 02 00 5a 58 5a 59 48 47 05 10 01 00 00 01 00 ff 01 00 00`) + N×16-byte AES-ECB blocks. First decrypted byte is a stray `\n`/`.` then the JSON begins; after the JSON's closing `}}` there's a short binary trailer (`00 01 00 00 11 00 00 00` in the sample — `0x11`=17 matches the exact block count, likely a block-count/length field, not meaningful payload).
- **Command `3503`** = sock telemetry push. Full decrypted JSON schema observed:
  ```json
  {"cmd":3503,"payload":{"rssi":-62,"wear":1,"sn":"T8340P00252008D1","time":1795151049,"oxy":0,"hr":0,"move":0,"move_val":0,"wear_val":0,"wear_threshold":0,"charge":1,"battery_vol":100,"signal_quality":0,"cur_sleep_start":0,"cur_sleep_end":0,"cur_sleep_duration":0}}
  ```
  Fields: `sn` = **sock's own serial** (T8340-prefixed, confirmed — first time we've seen it, previously invisible to the phone over BLE). `rssi` = BLE signal strength base<->sock. `wear`/`wear_val`/`wear_threshold` = worn-detection. `hr`/`oxy` = heart rate / SpO2 (0 when not worn/no reading). `move`/`move_val` = motion detection. `charge`/`battery_vol` = charging state and battery %. `cur_sleep_*` = active sleep session tracking. `time` = unix timestamp.
- This confirms the actual flow: **sock --BLE--> base --(decrypts/relays)--> phone, via PPCS P2P UDP, AES-ECB with the key derived from the base's serial**, logged in cleartext by the app itself. The BLE layer between sock and base remains a separate, still-undetermined encryption (not cracked), but it doesn't need to be — **the P2P channel already gives plaintext sock data once decrypted**.
- Ack packet format: `f1 d1 <len_LE16> d1 02 00 01 00 <seq_byte>` (phone->base, 11 bytes total, no payload) — just acknowledges receipt of a `d0` data packet by echoing part of its sub-header.

### How to reproduce / use this going forward
1. Capture UDP traffic between the phone and the base's IP (any interface, no port filter needed) while the app is open — a plain `tcpdump`/Wireshark capture on either end works, no Frida/root needed beyond running tcpdump.
2. Get the AES key once per base: open the eufy app with `adb logcat` running, grep for `HomeSecurity.*keyvalue=`, take the string, drop the trailing `-M`, use the first 16 ASCII bytes as an AES-128-ECB key.
3. For each `f1 d0` UDP packet, skip the first 24 bytes (header), AES-128-ECB-decrypt the rest, strip the leading stray byte and trailing block-count trailer, parse as JSON.
4. This should also work for **other command IDs** beyond 3503 (e.g. commands sent *to* the sock/base, config changes, historical session data) — same key, same framing, just a different `cmd` value and payload shape. Worth capturing a longer session to enumerate other `cmd` values.

## Cold-start capture: full session handshake decoded (2026-11-26, coldstart.pcap)
Force-stopped the app, captured broad UDP from before relaunch. The real handshake starts ~18.5s in (after cloud login/TLS traffic settles):

1. **Parallel discovery** (phone picks a fresh local port, e.g. 18201):
   - `f1 00 00 00` (4B) sent to **3 AWS relay candidates** (seen: `18.211.176.129`, `3.13.12.246`, `184.72.36.250`, all port **32100**) — cloud-assisted lookup path.
   - `f1 30 00 00` (4B) sent to **local broadcast** (`192.168.7.255` and `255.255.255.255`) on port **32108** — LAN discovery path, tried in parallel.
2. **Base answers the broadcast directly** (same LAN, so this wins the race): base replies from a **freshly chosen ephemeral port** (e.g. 15833) straight to the phone's port (18201) with `f1 41 0014 <20-byte announce body>` / `f1 42 ...` (repeats). The announce body is a fixed-looking tag, not JSON — not yet decoded further, but it's not session-specific (same bytes seen on different connects).
   - **This exchange is how you learn the base's current port** — critical for a standalone client. No pre-shared port needed; just broadcast and listen.
3. **Ping/pong starts immediately** on the newly learned (phone_port, base_port) pair: `f1 e0 00 00` / `f1 e1 00 00`, same as the steady-state keepalive already documented.
4. **First encrypted exchange**: phone sends `f1 d0 <len> d1 00 <msgid> 58 5a 59 48 <...sub-header...>` + one 16-byte AES-ECB block. Decrypts (same key as always, `524071D-333113-M`) to **`ff 00 00 00 01 00 00 00 00 00 00 00 00 00 00 00`** — a fixed capability/ready flag, not JSON. (This matches the mystery `\xff\x00\x00\x00\x01\x00...` bytes flagged as "undecoded" in the earlier general capture — now explained: it's the session hello, not telemetry.)
5. Base pushes a couple of **zeroed/placeholder device-info responses** (non-block-aligned payload lengths, e.g. 133/132/8 bytes — not standard AES-ECB block multiples, likely a different, not-yet-fully-decoded sub-format used only during bring-up, probably just "no data yet" placeholders). Not fully decoded, but immaterial — once the sock has reported, this transitions into the normal `cmd 3503`-style traffic already fully documented above.
6. From here on, traffic matches everything already catalogued (telemetry, settings pushes, acks via `f1 d1`).

**Conclusion: a fully standalone client is achievable.** The only thing an independent client needs that the app previously "hid" is step 1-3 — broadcast on the LAN, read the base's reply to learn its current port, ping it. No cloud dependency required for LAN-only operation (the AWS lookup is a parallel fallback, not a prerequisite — local broadcast wins first). No extra authentication beyond knowing the static AES key appears necessary for the base to start accepting `f1 d0` commands from the newly-discovered port.

## RESOLVED: full standalone telemetry + bulk dump working end-to-end (2026-11-20)
Root cause of the channel-2 puzzle, finally nailed:
1. **Fragment header length varies**: the first fragment of a message has a 24-byte header (includes the `XZYH` tag at offset 8); continuation fragments have only an 8-byte header (`f1 d0 <len> d1 <channel> <msgid>`), no tag. Using a fixed 24-byte skip for every packet corrupted continuation fragments.
2. **The base sends some content in plaintext, not AES-encrypted, to our standalone client** — confirmed by comparing raw (undecrypted) wire bytes directly: the bulk device-param dump came back as plain readable JSON bytes on the wire in our session, while the same message type was genuinely high-entropy ciphertext in the real app's session. Likely the base downgrades to no-encryption as a compatibility fallback for a client whose capability/hello negotiation it doesn't fully recognize (we're replaying a fixed captured hello, not implementing the real negotiation). Fix: just try both raw-as-JSON and AES-decrypted-as-JSON on every buffer; harmless either way since decrypting non-ciphertext just produces unparseable garbage that's discarded.
3. Channels must be buffered **and extracted independently in each of {plain, decrypted} forms** — four buffers per channel.
- **Result**: full clean JSON now flows through the standalone client for both channels — the 77-param + firmware-version bulk dump, and (importantly) **live `cmd 3503` sock telemetry with the sock confirmed worn**, e.g. `{"cmd": 3503, "payload": {"rssi": -57, "sn": "T8340P00252008D1", "wear": 18, "wear_val": 488, "wear_threshold": 1012, "battery_vol": 99, "sleep_state": 5, ...}}` — received with the official app completely force-stopped the entire time.
- **This closes out the core reverse-engineering goal**: a standalone, app-independent client reads live sock telemetry end-to-end. `scripts/standalone_client.py` in this repo reflects the fix.
- Remaining open item: our client still only *reads*. Sending a command (e.g. changing an alert threshold) from the standalone client, using the now-fully-understood `d0`/`d1`/ack protocol, hasn't been exercised yet — next logical step if write access is wanted.

## WRITE #2 confirmed: cmd 3516, and a key correction for generalizing to new commands (2026-11-20)
**`cmd 3516` (move_threshold) write confirmed working — but two things had to be fixed first, both important for every future command we test:**

1. **The 12-byte "subtype" field (right after the `XZYH` tag in the header) is per-command, not a universal constant.** It differs between `cmd 3515` (`460590000000010000010000`) and `cmd 3516` (`4605a000000001002c010000`). Reusing one command's subtype for another gets the packet **silently dropped with no ack at all** — this looked identical to "the base rejected my value" but was really "the base didn't recognize this as a valid packet shape". **Always grab the exact subtype bytes from a real captured example of the specific `cmd` you're testing**, never assume/reuse.
2. **JSON field order matters**: real packets are always `{"account_id":...,"cmd":...,"mChannel":...,"mValue3":...,"payload":{...}}` in that exact order. `build_command_packet()` now forces this order regardless of the caller's dict, rather than relying on Python dict insertion order from however the test JSON was written.
3. **Padding content is not always literal zero bytes** — real captured packets sometimes have non-zero garbage in the padding after the JSON's closing `}` (likely leftover/unzeroed buffer content on the app's side, not a checksum we need to replicate — tested CRC32/Adler32/MD5 of the JSON against it, no match). ## Cloud API TLS interception working (2026-11-20)
**Infrastructure milestone: can now read the app's HTTPS traffic to `care-app.eufylife.com`.**

### Setup that worked
1. `mitmdump` (installed via pacman) generates a CA cert at `~/.mitmproxy/mitmproxy-ca-cert.pem`.
2. **The app detects a configured system HTTP proxy and self-terminates immediately** (`System.exit(0)`, no exception) — confirmed by setting `settings put global http_proxy <host>:<port>` as root and watching the app die on launch; removing the setting let it open normally again. This is a real anti-MITM check, distinct from the earlier root/Frida detection.
3. **Workaround: transparent iptables DNAT on the phone instead of a configured proxy** — invisible to the app, since it's a kernel-level redirect the app has no API to query. `su -c 'iptables -t nat -A OUTPUT -p tcp --dport 443 -j DNAT --to-destination <host_ip>:8080'` (broad port-443 redirect; IP-specific rules don't work reliably since `care-app.eufylife.com` resolves to different CDN edge IPs each connection).
4. **The CA also needs installing as a *system* trust anchor**, not just a user-added one — the app's `network_security_config` (seen in the manifest findings right at the start of this project) only trusts the platform default (system CAs) in release builds. Since `/system` can't be remounted read-write on this device (dm-verity), used the standard Magisk-style workaround: copy `/system/etc/security/cacerts/*` to a writable location, add the new CA cert there (correct Android filename = `openssl x509 -subject_hash_old` output + `.0`, root-owned, mode 644, SELinux context `u:object_r:system_file:s0`), then `su -c 'mount -o bind <writable_copy> /system/etc/security/cacerts'`.
5. Run `mitmdump` in **regular mode, not `--mode transparent`** — transparent mode expects to query the original destination via a Linux kernel mechanism (`SO_ORIGINAL_DST`) that only works when mitmproxy runs on the *same machine* doing the NAT. Since the NAT happens on the phone and mitmproxy runs on a separate host, this fails silently (0 bytes captured, no error). Regular mode works fine here because it falls back to TLS SNI to route, which is present on every connection we care about.
6. The app keeps a **persistent connection for the session** — adding the DNAT rule mid-session does nothing until the app is fully force-stopped and relaunched (fresh TCP/TLS connections only).
7. Don't forget your own host's firewall — `ufw`'s default-deny INPUT policy silently dropped the phone's inbound connections to the proxy port until explicitly allowed (`sudo ufw allow from <phone_subnet> to any port 8080 proto tcp`). This looked identical to "mitmproxy isn't working" for a while.

### What's visible now
Full list of `care-app.eufylife.com` endpoints hit during normal app use: `get_push_servers`, `get_care_baby_devices`, `update_devs_info` (very likely the device-name-change endpoint and others), `passport/params`, `get_banner_info`, `get_news_num`, `get_popups`, `register_push_token`, `ota/get_app_version`, `review/app_push_check`, `logging/upload_events`, `logging/upload_tracking_events`, `family/get_invites`, `care/breastfeeding/get_reminder_list`, `care/breastfeeding/get_rhythm_curve_list`, `care/get_babyapp_retire_popup`.

Keep these local-only; do not commit raw capture files or paste live token values into the public repo.**

### The real blocker: request/response bodies are separately encrypted
Both request and response bodies are encrypted **on top of TLS** — not plain JSON. Response headers include `encrypt-algorithm: algorithm_first`, naming a specific (presumably proprietary) scheme. ### Immediate next step if continuing this track
Hook the app's own encrypt/decrypt function call via Frida (now that we have a working rooted-device toolchain from earlier in this project) to capture plaintext request/response bodies directly, rather than trying to reverse the algorithm from ciphertext alone.

## Cloud API crypto: hit a genuine wall, two findings worth recording (2026-11-20)

### Frida/ptrace is actively blocked for this app — confirmed, not a timing issue
Every `start_frida_session` attach attempt in this session failed with "Process not found", even when the target pid was independently confirmed alive via `adb shell ps` at the exact same moment. Checked `list_frida_processes`' own enumeration directly afterward: **the app's pid is simply absent from frida-server's own process list**, while every other running app (including unrelated ones like Brave, Play Store, GMS) appears normally. This rules out timing/race entirely — it's the app itself (almost certainly the same `ijm`/ijiami packer anti-tamper layer found at the very start of this project) actively hardening against ptrace-based introspection (e.g. `prctl(PR_SET_DUMPABLE, 0)` or an installed seccomp filter blocking `PTRACE_ATTACH`), not just detecting-and-exiting after the fact like the earlier `/proc/net/unix` check. **Standard Frida attach/spawn will not work against this target on this device**, regardless of setup correctness.

### Found where the ECC key material lives on disk — but it's wrapped in another layer
With root, `shared_preference_security.xml` (in the app's private data dir) contains:
- `ecdh-key<account email>` — a large (~290+ byte) hex blob, clearly too big to be a raw EC private key (32-66 bytes for common curves) — this is wrapped/encrypted at rest, not plaintext.
- `account_data_key` — similarly large, likely wrapped session/account data.

This confirms the on-disk storage has its **own encryption layer** protecting the ECC key material, on top of (1) the local PPCS AES-ECB scheme (cracked), (2) the cloud API's ECDH+AES-CBC+HMAC scheme (`libecc-encryption.so`, not yet cracked), making this now a **third, nested crypto layer** to get through before the cloud API's "algorithm_first" scheme could be replicated from a static key, even if we could read this file.

### Where this leaves the cloud-API crack
Realistic remaining options, roughly in order of effort:
1. **Build a native harness** that `dlopen()`s `libecc-encryption.so` directly and calls its plain-C exports (`GetPrivateKey`, `uECC_shared_secret`, `kdf_func`, `AES_CBC_decrypt_buffer_ctx`) outside the Android app sandbox entirely — sidesteps Frida/ptrace blocking since nothing is injected into the running app. Complication: the small size of `GetPrivateKey` (12 bytes) suggests it's a trivial getter, not the real on-disk decryption logic; the actual key-unwrapping likely lives in the JNI wrapper (`Java_..._getPrivateKey`, which needs a real `JNIEnv*`) or in Java code not in this `.so` at all — would need a faked/minimal `JNIEnv` to call it standalone, a known but fiddly technique.
2. **Repackage the APK with a Frida gadget** instead of attaching to the live process — avoids the ptrace-based attach path entirely, but risks tripping the packer's own integrity/signature checks differently (untested whether it would survive).
3. If the on-disk wrapping turns out to be **Android Keystore / TEE-backed** (common for "ecdh-key" style storage via `AndroidKeyStore`), extracting it is not realistically possible even with root — hardware keystores are specifically designed to resist this. Not yet confirmed either way.

This is a materially harder problem than everything cracked so far in this project (which all yielded to either a leaked static key or straightforward packet analysis). Recommend treating it as its own dedicated investigation rather than squeezing further into this session.

## Cloud API crypto FULLY reverse-engineered via Ghidra — only the private key value remains (2026-11-20)
Installed Ghidra 12.2 + rz-ghidra (`sudo pacman -S ghidra rz-ghidra`) and configured `GHIDRA_INSTALL_DIR=/opt/ghidra` in the `rea` MCP server's launch env (added to `~/.claude.json`'s `mcpServers.rea.env`, reconnect via `/mcp` to pick it up). This unlocked full pseudocode decompilation — raw Rizin disassembly alone wasn't tractable for this scheme.

### `eccDecrypt(JNIEnv, thiz, String data, String key, int dataLen)`
Converts `data` and `key` Java strings to C strings (their actual byte content — likely passed via a Latin-1/byte-preserving String encoding, not hex/base64 text, since the underlying crypto consumes them as raw binary, not ASCII), then calls native `DecryptECC(data, dataLen, outBuf, outLenPtr, key)`.

### `DecryptECC` — complete ECIES scheme, fully decompiled
Envelope format (total length = `dataLen` bytes, minimum 0x52=82):
- `[0x00:0x21]` (33 bytes): sender's **ephemeral EC public key**, SEC1 compressed format (1-byte prefix + 32-byte X)
- `[0x21:0x31]` (16 bytes): **AES IV**
- `[0x31 : 0x31+ciphertext_len]` (`ciphertext_len = dataLen - 0x51`): **AES-128-CBC ciphertext**
- last 32 bytes of envelope: **HMAC-SHA256 tag**, computed over `[0x21 : 0x21+16+ciphertext_len]` (IV‖ciphertext)

Key derivation:
1. `shared_secret[32] = ECDH(ephemeral_pubkey, OUR_private_key)` — this is the `key` argument passed in from Java (confirmed via `derive_S_from_PRI`'s decompiled logic: the private-key argument is treated as **raw 32 bytes**, not a hex/base64 string — so whatever Java passes as the `key` jstring must carry raw binary, likely via a byte-preserving String charset).
2. `kdf_out[48] = KDF(shared_secret, 32 bytes)` (`kdf_func`)
3. `AES_key = kdf_out[0:16]`, `HMAC_key = kdf_out[16:48]` (32 bytes)
4. Verify `HMAC-SHA256(HMAC_key, IV‖ciphertext) == received_tag`; if valid, `AES-128-CBC-Decrypt(AES_key, IV, ciphertext)`, strip PKCS7 padding → plaintext.

This is a genuinely solid ECIES design (unlike the local protocol's static AES-ECB key) — no shortcut exists in the scheme itself. **The only missing piece is the actual value of "our ECC private key"** (32 raw bytes) that the Java layer passes in as the `key` argument.

### Where the private key lives, and the real remaining blocker
- `GetPrivateKey()` (native) just returns a pointer to a static buffer, written only by `GenerateKeyForECC` (`uECC_make_key`) — so the native side doesn't independently load/decrypt anything from disk. The **Java layer** is responsible for retrieving the real key and passing it into `eccDecrypt` each call.
- The actual key material is almost certainly the `ecdh-key<account email>` entry in `shared_preference_security.xml` (found earlier) — a ~290-byte wrapped blob, far too large to be a raw 32-byte key, so it's encrypted at rest.
- **This is now the single blocking unknown**: how that SharedPreferences blob is unwrapped into the raw 32-byte private key. Two possibilities, not yet distinguished:
  1. A software scheme (same homemade-crypto house style as everywhere else in this app) — crackable statically if we can find the unwrap routine (likely in Java/Kotlin code in the still-packed DEX, not in this `.so` — would need the DEX unpacked, or the Frida-blocked dynamic route).
  2. Android Keystore / hardware-backed wrapping — if so, not extractable even with root, since TEE-backed keys are specifically designed to resist this.
- Next concrete step if continuing: check whether the blob's structure matches a known Android Keystore wrapped-key format (e.g. ASN.1/protobuf framing Keystore typically uses), which would settle (2) vs (1) without more guessing.

## Memory-read technique confirmed viable, but timing-sensitive — not yet captured (2026-11-20)
**Good news: reading the hardened app's live memory directly via `/proc/<pid>/mem` as root works fine** — confirmed by successfully reading real bytes from a mapped heap region. This is a genuinely different kernel code path from the `ptrace()` syscall Frida uses (file-based `read()` on procfs vs. `PTRACE_ATTACH`), and it is **not** blocked by whatever hardening stops Frida. This is a real, reusable way around the anti-Frida wall found earlier, independent of Keystore questions.

**Not yet successful at catching the key itself**, for a timing reason, not a capability one:
- `libecc-encryption.so` never appears by name in `/proc/pid/maps` — the packer's custom loader maps native code anonymously (consistent with the same evasion pattern seen everywhere else in this app).
- Searched every anonymous executable region in the process (`r-xp`/`rwxp` with no backing file) for known unique strings from the library (`"dataChar length"`, `"keyChar length"`, `"EccEncryption"`) — no match, even immediately after confirming a real `update_devs_info` request fired (new TCP connection to a `care-app.eufylife.com` IP observed).
- Most likely explanation: the library is loaded, used, and unmapped again within the single HTTP request's lifetime (well under a second) — our polling (checking `/proc/pid/maps` a few seconds after the user confirms an action) is simply too slow to catch the window it's resident in memory.

### Next step if picking this up again
Need **tight, automated polling** (e.g. a loop checking `/proc/pid/maps` every 50-100ms right as the network action is triggered) rather than human-paced "done, check now" round trips — or find a way to make the library's mapping linger (e.g. trigger many back-to-back cloud requests so it stays loaded, or check immediately after `netstat` shows a *new* established connection to the cloud IP, polling in the same breath rather than waiting for a chat round-trip). Once caught, the plan is unchanged: dump the live memory of wherever the library's `.rodata`/key material is sitting (or use the same /proc/pid/mem technique to scan for the 32-byte private key bytes being passed into `eccDecrypt`), and validate candidates against an already-captured ciphertext envelope + tag using the now-fully-understood ECIES verification logic.

## Tight-polling memory capture: ruled out, with a clear reason why (2026-11-20)
Built a proper native poller (`mapwatch.c`, compiled on-device via Termux's `clang`) to remove the shell-based poller's fatal flaw (the first attempt forked 4-5 processes per iteration — `cat`/`grep`/`diff`/`wc` — making it far too slow to be "tight": at Android's process-spawn overhead, 20,000 iterations could take 20+ minutes, not seconds). The native version does a raw `open()`/`read()`/`close()` loop with zero forking, confirmed via `ps` to peg a CPU core at ~95%+.

**Even this did not catch the library resident in memory**, across multiple attempts, including one with a confirmed live TCP connection to a `care-app.eufylife.com` IP at the moment of polling. Also corrected an earlier test-design mistake: `update_devs_info` (device name change) **never carried the `encrypt-algorithm` header** — the actual ECIES-encrypted endpoints are the automatic app-open/navigation calls (`get_push_servers`, `get_care_baby_devices`, `get_reminder_list`, etc.), not settings saves. Confirmed from the original `care-app.eufylife.com` endpoint list captured earlier.

**Likely explanation**: given everything else learned about this app's hardening (anonymous-only native library mapping, no filename ever visible in `/proc/pid/maps`, active ptrace-blocking), the executable window for the decrypted library is almost certainly measured in microseconds — e.g. allocate → decrypt into a buffer → `mprotect()` to executable just long enough to run → immediately revert/unmap. No amount of *polling after the fact* (however fast) can reliably observe a window that short from outside the process.

**What would actually work**: intercepting the `mprotect()` (or `mmap()`) syscall itself as it happens — e.g. an eBPF kprobe/tracepoint, or a seccomp-notify-based approach — rather than checking state after the fact. This is a materially different, bigger tooling investment (kernel-level tracing infrastructure) than anything used in this project so far, and is the realistic next step **if** this specific sub-goal (extracting the live ECC private key) is pursued further.

### Where this leaves the cloud API work, honestly
- The full ECIES scheme is completely understood and documented (envelope format, ECDH, KDF, AES-CBC, HMAC verification) — this is real, durable progress regardless of whether the key is ever extracted.
- Static extraction of the key is blocked (wrapped in `shared_preference_security.xml`, unknown whether software or Keystore/TEE-protected).
- Dynamic extraction via Frida is blocked (confirmed: app's pid absent from frida-server's own process enumeration).
- Dynamic extraction via plain `/proc/pid/mem` reads is **not blocked** (confirmed working), but the specific technique tried (polling `/proc/pid/maps` for a named or newly-appeared library mapping) does not catch the window.
- This specific sub-problem (get the raw 32-byte private key) is a well-scoped, understood, but genuinely hard open problem requiring kernel-level tracing tooling not yet built. Recommend treating as its own future project rather than continuing to iterate on userspace polling approaches, which have now been reasonably exhausted.

## gdbserver attaches successfully (ptrace itself is NOT blocked) — but app self-destructs on resume (2026-11-20)
Tested whether the earlier "Frida/ptrace blocked" conclusion was really a ptrace-level block, or just Frida-specific fingerprinting. Installed Termux's `gdbserver` + `libthread-db` (downloaded directly as `.deb`s via `curl --resolve`, bypassing broken DNS resolution in Termux's bionic-linked curl — see Toolchain gotchas below) and attached to the live `com.oceanwing.care.cam` process:

```
gdbserver --attach :1234 <pid>
# -> "Attached; pid = <pid>" / "Listening on port 1234"
```

**This succeeded** — confirms `ptrace(PTRACE_ATTACH)` itself is not blocked at the kernel/process level. This means the earlier Frida conclusion ("pid absent from frida-server's own enumeration") was almost certainly catching the *aftermath* of this same self-destruct mechanism (process already killed by the time Frida's enumeration or our checks ran), not a true attach-time block.

Connected a real GDB session (`target remote`) and set a breakpoint on `mprotect` (a safe, always-resolvable libc target, chosen specifically because the plan was to catch any memory region being flipped executable — the suspected mechanism behind the native-library's anonymous, short-lived mapping). **On `continue`, the process was SIGKILLed within ~1-2 seconds** — before the breakpoint ever fired. This matches the earlier-documented root-detection self-destruct pattern (`/proc/self/status`'s `TracerPid` field is almost certainly the check), just firing much faster here, likely because resuming after being stopped at attach gives the check loop its next cycle immediately.

**Net new understanding**: the anti-debug defense is a live polling check (probably on a timer/loop, checking `TracerPid != 0`), not an attach-time block. It applies uniformly regardless of which ptrace-based tool attaches (Frida or gdbserver) and kills the process within a few seconds of the tracer being present and the process actually running (not just stopped at a breakpoint).

### What would be needed to go further
To win this race, the detection check itself needs to be neutralized *before* it gets a chance to run after resume — options, in rough order of effort:
1. **Patch the check in memory while still stopped** (possible in principle — we have full memory write access via the same gdb session — but requires first locating the exact comparison/branch instruction for the `TracerPid` check, which means getting a static disassembly of whichever code performs it; not yet attempted).
2. **LD_PRELOAD a fake libc `fopen`/`read` that lies about `/proc/self/status`'s `TracerPid` line** — requires the hook to be in place *before* the app's own first read of that file, i.e. injected at process creation (zygote fork), not via a later attach. Needs a Zygisk module (Magisk) or equivalent process-creation-time injection, which hasn't been set up in this project.
3. Hardware watchpoint on the specific read/compare instead of a software breakpoint, to pause with less disruption — still has the same fundamental race unless combined with (1).

This is a well-scoped, understood blocker now, but a materially bigger next step (static analysis to find the exact check, then patch-before-resume or Zygisk injection) rather than another quick iteration. Recommend treating it as its own follow-up task.

## Three interacting anti-tamper self-destruct layers found via live ptrace patching (2026-11-20)
Following up on the gdbserver-attach finding: used GDB's `catch syscall` to intercept `kill`/`tgkill`/`tkill`/`exit_group` syscalls at entry and neutralize them (set the signal argument register to 0 before the syscall executes), hoping to keep the process alive long enough to catch the ECC library loading. Ran as a GDB batch script (`autopatch.gdb`/`autopatch2.gdb` under `work/magisk/`) via `gdb --batch -x script.gdb` against the still-listening `gdbserver`, since driving this interactively through REA's MCP wrapper hit MI protocol desyncs on multi-line `commands...end` blocks (had to kill the stray local `gdb` process and avoid the wrapper for this specific technique; `source <script>` in batch mode worked where interactive `commands` blocks over the MCP tool did not).

**Confirmed there are at least three distinct, apparently-interacting self-destruct mechanisms**, not one:
1. **`kill(own_pid, SIGKILL)`** called directly via the raw syscall (not libc's wrapper) from the packer's native code (address inside the anonymous-mapped `libexec.so`-adjacent region). Successfully neutralized by catching the syscall at entry and zeroing the signal argument (`x1`) before it executes.
2. **A deliberate `SIGSEGV`** (wild/invalid memory access, intentionally triggered, not incidental) on a second thread shortly after the `kill` attempt. When passed through unmodified to the app, this produces a genuine fatal crash (confirmed via Android's `debuggerd`/`crash_dump64` taking over the process to write a tombstone) — i.e. this is a real, working fallback kill mechanism, not an anti-debug trick that recovers on its own.
3. **A `SIGTRAP`** at a third site that proved fatal once mechanisms 1 and 2 were both patched around — passing it through (rather than stopping on it) let the kernel's default fatal action for an unhandled trap finish the job instead of the app's own handler (if any) running correctly.

Patching (1) alone let (2) finish the job unmodified. Attempting to also skip past (2) by advancing `$pc` by 4 bytes (all AArch64 instructions are fixed 4-byte width) kept the process alive through that point, but led to the previously-unseen (3) becoming fatal — strongly suggesting these three checks are **not independent**; patching one changes the state the next one's logic depends on (plausibly all three are stages of the same watchdog loop, and skipping a step properly requires understanding what state it was supposed to set up for the next one, not just suppressing the symptom).

### Key architectural finding: detection and kill are decoupled via a JNI callback, not one native function
Traced `FUN_72a9e10330` (a large detection routine: reads a proc-file, iterates lines, compares substrings against runtime-hash-decoded reference strings — this explains why `strings` found nothing in these regions: **reference strings are obfuscated/decoded at runtime via simple XOR/subtract constants** baked into the code as immediate values, e.g. `w8 = 0xb782`/`movk w8,#0x4431,lsl #16` then combined with loop state — matching the style already confirmed on the Java side in `a6.d.C()`/`a6.d.D()`'s custom byte ciphers). On a detected match, it assigns a numeric "detection code" (e.g. `0x3`, `0x7`, `0x9`, `0xffffffff` via a jump table) and calls either `FUN_72a9e21ffc(code, flag)` or `FUN_72a9e222c0(code, flag)` depending on a `w27==0x64` check (0x64=100, likely a mode/config flag).

`FUN_72a9e21ffc` is **not** a kill routine — it's a **JNIEnv* vtable dispatcher**: `ldr x8,[x21]` (loads `JNIEnv*` → function table) then `ldr x8,[x8,#offset]; blr x8`, using offsets (`0x30`, `0x108`, `0xb8`, `0xc8`, `0x388`, etc.) consistent with ART's `JNINativeInterface` layout (`FindClass`, `GetMethodID`/`GetStaticMethodID`-family, `CallXMethod`-family). It resolves a class/method via cached pointers (`adrp 0x72a9ed1000,#0xf98`/`#0xea8` — static global caches, standard JNI local-ref-caching pattern) and invokes it with the detection code and a context string as arguments.

**Conclusion**: this native module's actual job is **signal-gathering (proc-file scanning + obfuscated-string matching + likely su-binary/debugger/frida-port probing) and reporting via a JNI callback into Java code** — it does not itself execute the final `kill`/`tgkill`/`SIGSEGV`/`SIGTRAP` triad documented in the gdb session two nights ago. That triad's actual trigger site is downstream of this callback, most likely either (a) back in Java (plausibly feeding into the same `a6.d`/`SafeGuardThread` machinery, or a sibling class not yet located), or (b) in a different one of the remaining un-traced native regions (3, 4, 6) that executes once the Java side decides to act.

### Frida/Magisk operational gotchas on this device
- `start_frida_session` with `mode: attach` by OS-visible PID (`pidof`/`ps`) frequently fails with "Process not found" — **Magisk's Zygisk/DenyList hides the app's real package name from Frida's own `device.enumerate_processes()`**, even though plain root `ps`/`pidof` sees it fine. `mode: spawn` (by package name) works reliably instead, since it intercepts at the zygote fork point before any hiding applies.
- **`spawn` mode's reported `pid` does not match the real final app process's OS pid once zygote specialization completes** — the session's `pid` field is for an intermediate pre-specialization handle; the true app pid must be read via `pidof`/`ps` after resume. A `logcat` "Process ... has died" line for the frida-reported pid is this intermediate handle's normal exit, **not** the real app dying — a dangerous false-positive trap that led to a premature "it worked" conclusion mid-session before catching it.
- `start_frida_session`/`load_frida_script` consistently report `state: "detached"` and an empty `messages` array immediately after a spawn+load+resume sequence — this is normal for this REA/Frida integration's handoff model, not a sign of failure; the injected script keeps running in the target process after the controlling session object detaches, but further async `send()` output from it is no longer captured by that session view.
- `frida-server` occasionally needs a restart (`kill -9` + relaunch) after several spawn/attach cycles in one sitting — repeated "Unexpectedly timed out while waiting for app to launch" errors on `start_frida_session` were resolved by simply restarting the server process.

### Why hooking only `doAttackStrategy` (first attempt) was insufficient
`doAttackStrategy` has exactly **one static call site** in the whole decompiled app (`b0.java`, the Magisk-isolated-service callback) — and that site passes `strategy=NONE(1)`, itself already a no-op. All other triggers reach it via **native JNI calls** (confirmed earlier via Ghidra tracing of `FUN_72a9e21ffc`'s JNIEnv* vtable dispatch), which a Java-level `.implementation =` override *does* correctly intercept (ART resolves JNI's `CallStaticVoidMethod` through the same patched method slot). However, organic on-device testing initially seemed to show the hook "not working" — the real cause was a **second, fully independent kill path**: the `SafeGuardThread` watchdog (`d3.n`, documented two nights ago) polls every 300ms and calls `System.exit(0)` directly on `Debug.isDebuggerConnected()` or the `TracerPid` check (`a6.d.G()`), with **zero involvement from `doAttackStrategy`**. Frida's own spawn/instrumentation footprint was plausibly tripping this separate watchdog, killing hooked test processes at unpredictable delays (13s–90s+) that looked like "the hook failed" when it was actually a different, unhooked mechanism firing.

### Final hook (all three chokepoints) — confirmed effective
```javascript
import Java from 'frida-java-bridge';
Java.perform(function () {
    Java.use('com.ijm.detect.drisk.unexp.NativeToolH')
        .doAttackStrategy.overload('android.content.Context', 'int', 'int')
        .implementation = function (context, i, i2) { return; }; // no-op
    Java.use('android.os.Debug').isDebuggerConnected.implementation = function () { return false; };
    Java.use('a6.d').G.implementation = function () { return false; };
});
```
Organic (real-detector-triggered) testing proved too timing-flaky to use as a clean before/after signal — both hooked and unhooked instances sometimes survived, sometimes died, at inconsistent delays, because the underlying native detectors' own timing is non-deterministic. The decisive, reproducible test instead **directly invoked the real call** via Frida (`NativeToolH.doAttackStrategy(context, 5 /*DIRECT_EXIT*/, 12 /*MAGISK*/)`) under controlled conditions:
- **Unhooked**: real app process killed in ~6 seconds (`AndroidRuntime: VM exiting with result code 0` — exact match to the `Process.killProcess`+`System.exit` source read two nights ago).
- **Hooked** (identical call, identical parameters): process alive and stable for 70+ seconds post-call, zero death events.

This is a clean, repeatable, source-level-verified demonstration that the three-point hook neutralizes the kill switch for any caller (native-JNI-triggered or direct) going through these three chokepoints. Scripts retained at `work/frida_project/hook.js` (production hook) and `test_hooked.js`/`test_unhooked.js` (the controlled A/B test harness), with their compiled bundles alongside.

### Root cause, more precisely
Android 16 appears to enforce stricter limits on attaching a JVMTI plugin (which is how Frida's Java bridge gets class-redefinition / method-hooking capability) to an **already-running, non-debuggable** process than prior Android versions did. `frida-java-bridge`'s own code has a `withoutDebuggableTransition` function name, implying its authors are aware of and specifically handle this exact scenario — but on this Android 16 build, it's either insufficient or hits an edge case. Frida's `spawn`-mode gating (pausing the process at the earliest possible point before any app code runs) was expected to give the JVMTI plugin the earliest possible attach point, but the logcat warning ("loaded too late") suggests even that isn't early enough on this ART build — possibly a fundamental limitation on Android 16 rather than a timing bug fixable by adjusting when/how our scripts load.

## Genuine native anti-tamper kill mechanism confirmed and partially dissected (2026-11-21)
With a real persistent attach (not REA's detach-after-resume), the app's actual defenses engage properly — and kill the process via raw `SIGKILL` (signal 9, confirmed via logcat, not the Java `System.exit(0)` path) within ~0.6 seconds of resume in the simplest case. This is the exact mechanism documented on night one ("kill(own_pid, SIGKILL) called directly via the raw syscall, not libc's wrapper") — now reproduced and investigated via Frida/Stalker instead of gdb, independently confirming night one's conclusions with new specifics:

### libc-level hooks cannot see any of this
Hooking `kill`/`tgkill`/`raise`/`open`/`read` etc. via `Interceptor.attach` on their libc exports **never fires** for the actual kill, nor for the native unpacker's own `mmap`/`mprotect` calls — confirmed directly via Ghidra: pulled the on-disk `libexec.so`/`libexecmain.so` (the ijiami unpacker's shellcode loader, real files at `/data/data/<pkg>/files/`, unlike the main payload's pure in-memory mapping) and found their `mmap`(syscall 0xde=222)/`mprotect`(0xe2=226) calls are **raw inlined `svc #0` instructions**, bypassing libc entirely — the same evasion pattern as the kill call. `libexec.so`/`libexecmain.so` themselves contain only the generic mmap→decrypt→mprotect→jump loader scaffolding (confirmed via Ghidra instruction trace of all 5 genuine `svc` sites in the file); the actual anti-tamper/kill *payload* is further decrypted into pure anonymous memory by this loader and was not captured as a separate file.

### Stalker-based raw-syscall interception: real progress, same multi-layer wall as night one
Built `work/frida_project/stalker_block.js`: uses `Stalker.follow(tid, { transform })` to intercept every `svc` instruction regardless of which (if any) libc function issues it, on specific threads, neutering `kill`/`tgkill`/`tkill` (syscalls 129/131/130) by zeroing the signal argument before the real syscall executes — same technique as the proven-working gdb `catch syscall` approach from night one, just via Frida.

Working through this surfaced two genuine new implementation pitfalls (now solved) and one confirmed recurrence of night one's core finding:
1. **`Process.getCurrentThreadId()` inside a Frida script returns Frida's own injected agent thread's tid, not the app's real main thread** — following that thread via Stalker does nothing useful; must explicitly enumerate and follow the app's actual threads (`tid == pid` for the main one).
2. **Eagerly `Stalker.follow()`-ing pre-existing ART-internal threads (binder, GC, JIT compiler, etc.) crashes the process with a genuine `SIGSEGV`** inside Stalker's own instruction-rewriting of binder IPC code — not a detection, a real Stalker/binder incompatibility. Fixed by filtering on thread name (skip anything matching `binder`, `Signal Catcher`, `Jit thread pool`, `HeapTaskDaemon`, etc.) before following.
3. **Binder thread-pool growth happens via raw `clone()` (syscall 220), not `pthread_create`** — same libc-bypass pattern as everything else security-relevant in this app. A `pthread_create` hook alone misses these; detecting the `clone` syscall directly in the Stalker transform and reading the child tid from `x0` on the instruction immediately following the `svc` (available in the parent right after the syscall returns) is required to catch new threads at all, native or binder. The new thread's name isn't set yet at the instant of `clone()` returning — must defer the follow-or-skip decision slightly (`setTimeout(..., 100)`, which **does** work correctly through the standalone driver) to let `prctl(PR_SET_NAME)`/`pthread_setname_np` run first, otherwise the same binder-thread Stalker crash recurs.
4. **Even with all of the above fixed** (main thread followed correctly, binder/ART-internal threads correctly identified and skipped, clone-chain threads correctly tracked), **the actual `SIGKILL` still gets through**, still immediately after `libexec.so` loads, on some thread never observed issuing a dangerous syscall through our instrumentation. This is the same wall night one hit with gdb: "every fix so far has just exposed the next layer rather than reaching a stable, debuggable state" — now independently reconfirmed via a completely different tool and technique.

### Assessment
Tonight's work materially deepens the understanding of *how* this kill mechanism evades tracing (libc-bypassing raw syscalls throughout, including for completely mundane operations like `mmap`/`mprotect`/thread creation, not just the kill itself — a much more pervasive pattern than night one characterized), and proves a real, working technique (Stalker-based raw syscall interception) for neutering *known* dangerous syscalls on *followed* threads. But it does not yet defeat the actual kill, for the same root reason night one concluded: the real check-and-kill sequence is not yet statically understood, so there's no way to know which thread(s)/code-path(s) still need following, or whether (echoing night one's three-layer finding) a *different* kill mechanism entirely (e.g. a deliberately-triggered `SIGSEGV`, which is a CPU fault Stalker's `svc`-only interception cannot see at all) is what's actually firing here.

**Recommendation unchanged from night one**: the realistic next step is static disassembly of the actual decrypted payload (not the `libexec.so`/`libexecmain.so` loader scaffolding, which is now fully understood and uninteresting) — which requires solving the separate, specific sub-problem of catching that payload while it's transiently mapped in memory. Frida's `Interceptor.attach` on the loader's own `mprotect` call (now that we know its exact location: `FUN_00196cd4`/`FUN_00196f68` in `libexec.so`, syscall `0xe2` sites) is a concrete, scoped way to do this — read the about-to-be-protected memory region as data (no execute permission needed to read) in the instant before the `mprotect` syscall executes, which should capture the real payload without needing Stalker or any further thread-chasing. Not yet attempted; a good, bounded next step if this specific sub-problem is picked up again, but distinct from (and more promising than) continuing to iterate on live kill-interception.

## mprotect-dump technique validated: real anti-tamper payload captured as static data (2026-11-21)
Extended `stalker_block.js` to intercept `mprotect` (syscall `0xe2`=226, also a raw inlined syscall, confirmed via Ghidra) on the followed main thread: in the instant before a `PROT_EXEC` mprotect executes, read the target memory region **as plain data** (no execute permission needed to read) and write it to a file. This successfully captured the real anti-tamper payload that all of tonight's and night-one's live-hooking attempts could never catch directly — confirmed via Ghidra: **1104 real procedures** recovered from a 692KB dump (`mprotect_dump_0x78e851d000.bin`), vs. zero/garbage from every earlier attempt at catching this module resident in memory by polling.

This is a genuinely new, durable capability: **any transiently-mapped encrypted native payload in this app can now be captured** by this technique, regardless of how short its executable window is — the previous "polling is too slow" conclusion (documented earlier tonight and on night one) only applied to *after-the-fact* polling; intercepting the exact `mprotect` syscall that flips a region executable sidesteps the timing problem entirely, since Stalker is already resident on the thread issuing that syscall.

### What was found in the captured anti-tamper payload
Searching the dump for the exact `movz x8, #0x81; svc #0` instruction pair (kill=129) found **90+ genuine occurrences** throughout the 692KB module (confirmed several directly via `read_bytes`, not an artifact of the search pattern). Distinguishing the real destructive call (if any exist among these sites) requires decoding each site's signal argument (`x1`/`x2` register setup a few instructions earlier) individually — not completed, given the volume (90+ sites) and diminishing returns versus the broader goal.

## EXACT kill mechanism fully decoded via static analysis of the captured payload (2026-11-21)
Opened `mprotect_dump_0x78e851d000.bin` (692KB, 1104 procedures, captured earlier tonight) in Ghidra via REA and read the raw instructions of `FUN_78e851e018` — one of the ~90 `svc`-containing functions found earlier. This single function is the complete self-destruct mechanism, explaining every layer documented on night one and tonight:

1. **Conditional `ptrace()` self-check** (syscall `0x65`=101), gated on the function's second argument `== 5` AND a flag byte at a fixed global offset (`[global+0x1e3]`).
2. **A dynamically-computed callback redirect**: if a separate global pointer is non-null and a flag byte at offset `0x1ee` within it is set, the function `br`s to an address built from a small lookup table combined with the original argument — almost certainly the path that reaches the JNI callback → `doAttackStrategy`/`Strategy` dispatch chain fully decoded earlier tonight, rather than the raw-kill path below.
3. **`kill(pid, 9)` raw syscall** (`mov x8, #0x81` = 129 = kill; `mov w1, #0x9` = SIGKILL) — the exact mechanism from night one ("called directly via the raw syscall, not libc's wrapper").
4. **Unconditionally followed by `brk 0x1`** (software breakpoint → SIGTRAP), reached via every code path regardless of whether the `kill()` syscall above succeeded or failed. The MBA-obfuscated polynomial arithmetic (`(iVar3+1)*iVar3*(iVar3+2)*...` style, a disguised divisibility/range check) sitting between the `kill()` call and the final `brk` is misdirection — every branch of it eventually reaches the same terminal `brk 0x1` instruction at `0x78e851e3a0`.

### Why the SIGSEGV/SIGTRAP exception handler added earlier tonight didn't reliably help
`Process.setExceptionHandler()` installs a *userspace* handler that's just one link in the process's signal-handler chain. Android's own crash-handling infrastructure (debuggerd/tombstone) typically installs its own `SIGTRAP`/`SIGSEGV` handlers very early in process lifetime, often before Frida's injection completes — so there's a real race for which handler sees the signal first, and a specific `brk` immediate value (`#1` here) may be treated specially by that earlier-installed chain in a way a later-installed Frida handler can't reliably preempt. This is consistent with — and now gives a precise mechanical explanation for — the earlier-documented high variance in exception-handler effectiveness.

### The actual fix: skip the `brk` instruction at the Stalker-instruction level, don't rely on catching the resulting signal
Since `Stalker.follow`'s `transform` callback already sees every instruction on a followed thread (proven working for `svc` interception tonight), the robust fix is to detect `instruction.mnemonic === 'brk'` in that same transform and **not emit it at all** (skip rather than `iterator.keep()`), preventing the trap from ever reaching the CPU/signal-delivery layer in the first place — sidestepping the signal-handler race entirely rather than trying to win it after the fact.

**Conclusion: full Java-level hooking (Java.use()/method interception via frida-java-bridge) is not achievable against this specific non-debuggable release build on Android 16, by any means tried or found.** This is a structural platform limitation, not a timing or configuration issue.

**This does not block the overall ECIES-key-capture goal.** `eccDecrypt`/`DecryptECC` (see "Cloud API crypto FULLY reverse-engineered via Ghidra" above) is pure native code — the Java layer only marshals `jstring` arguments into C strings before calling it. Capturing the 32-byte private key argument (or the decrypted plaintext) only requires a **native** Interceptor hook on `DecryptECC`'s address once `libecc-encryption.so` is mapped executable — no Java bridge, no JVMTI, no ART offsets needed at all. Pivoting fully to this native-only path (same mprotect-dump + Stalker-based survival technique already built for the anti-tamper payload, just watching for a second library's mprotect call and placing a real-time hook instead of a one-shot dump).

## MAJOR BREAKTHROUGH: the kill is tied to Activity-launch specifically, not general process presence (2026-11-21, continued)
Live-logcat correlation (see above) incidentally caught Android's own Zygote auto-spawning a SECOND, completely separate instance of this app in response to the `com.evernote.android.job.JobBootReceiver` broadcast (an unrelated background job-rescheduler library, not triggered by us) — and that second process ran **completely unkilled** through `libhome_security.so` (`JNI_OnLoad`, `reg_native_methods`), `libflutter.so`, Google Play Services Dynamite modules, MMKV, everything — while every Frida-*spawned* instance (which launches via `SplashActivity`, the real UI entry point) consistently dies within ~1-9 seconds.

**Confirmed via direct, repeated testing**: triggering the app via `am broadcast -a android.intent.action.BOOT_COMPLETED -n com.oceanwing.care.cam/com.evernote.android.job.JobBootReceiver` (any non-Activity component works) instead of `am start .../SplashActivity`, with **zero Frida involvement**, survives reliably — **5/5 trials** still running after 6+ seconds untouched, one ran 30+ seconds. The fast self-destruct is specifically wired to the Activity/UI launch path (almost certainly `Application.onCreate()` or `SplashActivity.onCreate()`), not a general always-on watchdog.

**New blocker found, but it's a much better one**: Frida's `device.attach()` (as opposed to `spawn()`) on an already-running broadcast-spawned process reliably **times out** ("Unexpectedly timed out while waiting for stop from process") rather than crashing anything — confirmed Magisk's denylist is not even enforced (`magisk --denylist status` → "Denylist is not enforced"), ruling that out as the cause. This is a **mechanical Frida/ptrace injection limitation** (likely too many live threads by the time we attach, or this device/app's thread-suspend handshake is just slow), not a security detection — the target process survives every failed attach attempt untouched (confirmed repeatedly, same pid persists across 3+ consecutive failed attach attempts in a row). Attaching very early (1-8s) sometimes crashes the process instead of timing out cleanly — there's a narrow danger window early in the broadcast-triggered process's life too, but it's avoidable by waiting ~10+ seconds before attaching.

**This reframes the whole problem**: we no longer need to defeat the anti-tamper kill mechanism at all. We need to defeat a plain Frida injection timeout against a long-lived, otherwise-uninstrumented process. This is a well-understood, generic Frida problem (not specific to this app's defenses) with known mitigations: smaller/targeted injection, a different Frida version, `frida-gadget` (load the agent via an injected `.so` at a point of our choosing instead of ptrace-attach), or possibly just a longer client-side timeout/retry than frida-node's default.

**Recommended next step**: once attach succeeds, the plan is unchanged from before — our `poll_block.js` script (already loaded, no Stalker, already carries the 42-site kill patch and the `DecryptECC` native hook) would be live inside a process that can safely be driven all the way to a real network call (e.g. by then sending an explicit `am start .../SplashActivity` intent to the *already-running, already-safely-attached* process, or just waiting for its own background job/network activity to fire), with no risk of the Activity-launch kill since Frida is already resident before anything triggers it.

## Further correction: broadcast-spawned process survival is NOT Frida-proof either — likely Android's own responsiveness watchdog, not app-level anti-tamper (2026-11-21, continued)
Follow-up testing complicates (and partially corrects) the "Activity-launch-specific kill" theory above:

- **Pure survival baseline is solid**: 10/10 trials of `am broadcast` (JobBootReceiver), with zero Frida involvement, survived a full 9 seconds untouched. Confirmed via logcat that this process has a natural ~10s lifecycle and calls `System.exit(0)` cleanly on its own once the background job work finishes — not a security kill, just normal `evernote-android-job` library behavior. So **this specific entry point is actually unsuitable for reaching real app logic anyway** — it never runs the real UI/network code, just a generic job-rescheduler.
- **But Frida `attach()` against it is still unreliable**: repeated attempts to attach within the first ~2 seconds produced an almost-immediate `signal 9 (Killed)`, with logcat showing `ActivityManager: Process ... has died: prcl TRNB` right at the same moment — i.e. **the attach attempt itself appears to trigger the kill**, just like the Activity-launch path.
- **New working hypothesis, more mundane than deliberate anti-tamper**: Frida's ptrace-based attach has to stop every thread in the process simultaneously (confirmed ~54-59 threads present within 1 second of launch — Flutter alone spins up a lot immediately). If that stop-the-world takes too long on this device/app, Android's own responsiveness watchdogs could plausibly kill the process as "unresponsive" — this would apply to *both* a foreground Activity (ANR-style) and a background JobScheduler-triggered process (job-exceeded-time-budget-style) without requiring any deliberate detection logic in the app at all. This would mean a large fraction of tonight's (and prior sessions') "anti-tamper kill" fighting may have actually been fighting **generic Frida/Android interaction overhead**, not (only) bespoke app defenses — the native kill-site patch and SIGSEGV race are real and separately confirmed, but this specific fast, consistent death might be a different, simpler mechanism layered on top.
- Not yet distinguished from "still app-level detection, just also keyed off attach specifically" — would need a verbose frida-server log capture of a failing attach (attempted via `-v`, but output was empty/not captured through our redirect — needs a cleaner capture method, e.g. logcat with a frida-specific tag, not yet found) or a controlled test with a trivial/non-hardened app to see if the SAME attach-triggers-kill pattern reproduces against an app with no anti-tamper at all (which would confirm the "generic Android watchdog" theory conclusively).

**Net assessment**: this entry-point pivot didn't produce a clean win yet, but it did produce a cleaner, more specific question (is this Android's own watchdog reacting to ptrace-freeze, or the app?) that's answerable with a simple control experiment (try the same attach-timing pattern against an unrelated, unprotected app) rather than continuing to guess inside this one hardened target.

## frida-gadget (zero ptrace) tested directly — dies at the identical instant regardless of injection method (2026-11-21, continued)
Switched tooling entirely per user direction: installed `apktool` (AUR `android-apktool-bin`) and Android `build-tools` (AUR `android-sdk-build-tools-33.0.2`, giving `zipalign`/`apksigner`), then used `objection patchapk` (via `pipx`) to inject `frida-gadget` (v17.23.2, matching our `frida-server`) directly into the APK's `s.h.e.l.l.S` Application class static initializer — the earliest possible code in the whole process, running via a completely normal `dlopen()`/`System.loadLibrary()`, with **no ptrace, no spawn-gate, no attach at all**.

- Had to hand-fix two objection bugs: it wrote the gadget to `lib/arm64/` instead of the correct `lib/arm64-v8a/` ABI folder, and the original manifest's `android:requiredSplitTypes="base__abi"`/`android:isSplitRequired="true"` attributes (left over from the original split APK) caused `INSTALL_FAILED_MISSING_SPLIT` against our merged single-APK build — removed both by hand via a second apktool decompile/edit/rebuild pass, re-signed with a fresh debug keystore.
- **First real success**: confirmed via `/proc/pid/maps` and `netstat` that the gadget loads and listens on `127.0.0.1:27042` inside the device, and the process survived 8+ seconds untouched the first time (long enough to prove the injection itself isn't instant death) — but then died from Android's own process-start-timeout ("Process ... failed to complete startup" → "Killing ... bg anr") because the gadget's default `on_load: wait` blocks app startup until a client connects, and we weren't fast enough to connect before that framework-level timeout (~15s) elapsed. Fixed by connecting via a Frida-node driver immediately after launching, with a short retry loop (`frida.getDeviceManager().addRemoteDevice('127.0.0.1:27042')` → `device.attach('Gadget')`).
- **Once we connect fast enough, the process still dies — in well under 100ms, right as `libexecmain.so` (the packer's own native payload) loads**, every time. Tried two independent countermeasures, both cheap to test and both ineffective:
  1. Renamed the gadget file and its `loadLibrary()` string from `frida-gadget`/`libfrida-gadget.so` to an innocuous `coreutil2`/`libcoreutil2.so` — same instant death.
  2. Changed the gadget's listening port from the well-known default 27042 to an arbitrary 48291 via a `libcoreutil2.config.so` config file — same instant death.
- **This is the key new finding**: the death happens at the *identical* moment and *this fast* regardless of injection mechanism (ptrace spawn, ptrace attach, or zero-ptrace dlopen-based gadget) and regardless of gadget naming/port. That rules out TracerPid, ptrace-specific detection, and simple Frida-artifact-name/port scanning as the mechanism — all three are now directly falsified by this gadget-mode result, not just inferred. The most likely remaining explanation is a **loaded-library enumeration/whitelist check** baked into the commercial iJiami-style packer (`libijmdetect-drisk.so`/`libijm-emulator.so`, already known to be present in this APK) — i.e. it walks `/proc/self/maps` (or equivalent) at native-payload-init time and kills the process if it finds *any* unexpected shared library loaded, independent of that library's name, port, or ptrace status. A gadget (or any other injected `.so`) will always show up as exactly such an unexpected entry.

**If this hypothesis is right, defeating it would require the gadget's code not to appear as a separately-loaded shared library at all** (e.g. merging it into an existing, expected library's binary instead of adding a new `.so`) — a substantially bigger lift than anything tried tonight, and not yet attempted. Good stopping point to get human input before committing to that scale of effort.

## Isolated the real trigger: it's Frida/Gum's own runtime footprint, not any artifact we can disguise (2026-11-21, continued)
Ran a clean, controlled sequence of tests to narrow down exactly what's being detected, each a cheap one-variable change from the last:

1. **Inert distractor library** (hand-compiled with bare `clang --target=aarch64-linux-android21 -nostdlib`, 2.5KB, does nothing but exist — no Frida code at all, same injection point as the gadget) — **the app ran completely normally**: real UI (`EufyPolicyActivity`), app-specific lifecycle logs (`BABY_RETIRE`), GC, WiFi activity, no kill at all, for as long as observed. This conclusively rules out "any extra/unexpected loaded library kills it" (the iJiami-whitelist theory from the previous entry) — a harmless extra `.so` is completely fine.
2. **frida-gadget in `script` interaction mode** (via `objection patchapk -c <config> -l poll_block.js`, using `"type": "script"` instead of `"type": "listen"`) — **no TCP socket opens at all** (confirmed by the absence of the `Frida: Listening on 127.0.0.1` logcat line that appeared in every `listen`-mode run) — **still dies at the identical instant**, right as `libexecmain.so` loads. Rules out "detects the listening socket" as the mechanism too.
3. **Same script-mode gadget, but with a truly empty script** (`send('[empty] script loaded, doing nothing else');` — no `Interceptor.attach` calls at all, not even our own `kill`/`tgkill`/`sendSignal` hooks) — **still dies at the identical instant**. Rules out "it's specifically our hooks on signal-related functions" as the mechanism.

**Conclusion**: across renaming, re-porting, removing the network listener, and removing every hook our own script installs, the only thing that reliably distinguishes "survives" from "dies at the identical ~instant, every time" is whether **Frida/Gum's own runtime is present and initializing at all** — not any disguisable artifact (name, port, socket, our own hooks). The most likely remaining mechanism, consistent with this app's known iJiami-family protection, is a scan for something intrinsic to Gum's runtime itself — most plausibly **RWX (simultaneously writable+executable) memory regions**, which Frida's Gum library allocates by default for its Interceptor/Stalker trampoline pools regardless of what a loaded script does, and which is one of the most standard, well-known generic anti-Frida heuristics (legitimate app code essentially never needs W+X memory at the same time). This app's own packer was already observed earlier this session going out of its way to avoid ever instantiating memory as RWX directly (always transitioning RW→RX via a separate `mprotect`, never allocating RWX up front) — consistent with its authors specifically defending against exactly this kind of scan.

**This is no longer something fixable by repackaging tricks.** Defeating it would mean one of: (a) patching Frida's own Gum library to avoid RWX trampoline allocation (an upstream Frida engineering change, not an APK-side one), (b) finding and neutralizing the specific scan itself via static analysis of `libijmdetect-drisk.so` (a new, separate reverse-engineering target, not yet attempted), or (c) abandoning live Frida instrumentation for this specific goal and pursuing the private key through a different route entirely (e.g. static analysis of the SharedPreferences-wrapped ECDH key material, which a much-earlier session entry flagged as the key still-unresolved question — Keystore-wrapped vs. software-wrapped).

## Gum-patching attempt: built it, isolated a real bug, but hit a different hard blocker — pivoting to reverse-engineering the detector itself (2026-11-21, continued)
Built frida from source (cloned `frida/frida` tag 17.23.2 with submodules, ~1GB; installed `meson`/`ninja` via `yay`; downloaded Android NDK r29, ~780MB, with explicit user approval first) targeting `android-arm64`, gadget-only (`--enable-gadget --disable-frida-tools --disable-server --disable-inject --disable-graft-tool`).

**The patch**: `gum/gummemory.c`'s `gum_query_rwx_support()` hardcodes `GUM_RWX_FULL` for every platform except Darwin-without-i386. Changed the condition to also return `GUM_RWX_NONE` for `HAVE_ANDROID`, forcing `gumcodeallocator.c`'s existing RW→(write code)→`gum_mprotect(..., GUM_PAGE_RX)` commit path — the exact "never simultaneously writable+executable" pattern this app's own packer uses — instead of the direct `GUM_PAGE_RWX` allocation Gum otherwise does on Android by default. One-line patch, confirmed to compile and link cleanly, confirmed the resulting `frida-gadget.so` is byte-structurally the same kind of artifact as the official release (`file` reports identically: stripped, NDK r29, Android 21 target).

**Control test confirmed the build pipeline itself is sound**: built an *unpatched* gadget through the exact same from-source toolchain and it worked identically to the official downloaded one — loads, spins up its threads (`frida-gadget`, `gmain`, `pool-frida`, `gdbus`, all in normal `S` (sleeping) state within 0.6s), opens its listen socket within ~4s. So the from-source build process itself introduces no regression.

**The patched build hits a different failure mode entirely** — not a kill, a true hang: the whole process (every thread) enters kernel state `T (stopped)` within 0.6s of spawn, `TracerPid: 0` (nothing has ptrace-attached), and **does not resume even after manually sending it `SIGCONT` from a root shell**. Android's ActivityManager eventually gives up after ~15s ("Process ... failed to complete startup") and kills it — but that's a downstream symptom, not the real bug; the real bug is whatever keeps re-asserting the stop. The unpatched build never enters this state at all at the same 0.6s mark (confirmed side-by-side, same device, same APK otherwise).

Traced the suspicious-but-innocent leads and ruled them out:
- `gum_code_segment_is_supported()` returns `FALSE` unconditionally on non-Darwin-jailbreak platforms, so the patch cannot be accidentally routing into Darwin's `GumCodeSegment` path on Android (confirmed by reading the source directly).
- Found all 19 real call sites of `gum_query_is_rwx_supported`/`gum_query_rwx_support` project-wide via `rg` (a from-scratch, non-`find`/`grep` search was needed — `find`/`grep` kept getting silently swallowed by an unrelated environment noise issue documented earlier this session). Three ARM/ARM64/x86 Stalker backends also cache this flag (`self->is_rwx_supported`), which is a plausible secondary place something assumes Android-is-always-RWX and misbehaves, but Stalker isn't initialized at all during this early hang (it happens before the gadget even spins up its own threads).

**This is now a real, separate Frida/Android engineering bug** (something about disabling RWX on Android causes the whole process to freeze at the kernel signal level within well under a second, before Gum even gets to its own thread-creation step) — not something resolvable with a quick second patch attempt, and arguably not productive to keep debugging blind without Frida's own test infrastructure or upstream issue-tracker context.

**Per plan, pivoting to the fallback: reverse-engineering `libijmdetect-drisk.so`/`libijm-emulator.so` directly** (the iJiami-family anti-tamper/anti-hook libraries already identified in this APK) to find and neutralize the specific RWX-memory (or whatever it actually is) scan at its source, rather than trying to make Gum avoid the behavior being scanned for.

## BREAKTHROUGH: survival solved — renaming one thread name was the actual fix (2026-11-21, continued)
The RWX-disabling gum patch caused a separate, serious hang bug (documented above) and was reverted. Pivoted to a much smaller, safer patch based on a new lead: GLib's `g_thread_new("frida-gadget", ...)` call in `frida-core/lib/gadget/gadget-glue.c:115` names the gadget's own worker thread literally `"frida-gadget"` — a highly distinctive, exact, well-known string (this is Frida's own public, widely-documented default thread name). Patched it to `"coreutil-worker"`, rebuilt (same from-source toolchain, RWX patch cleanly reverted via `git checkout`), repackaged into the APK, reinstalled.

**Result: the process survives.** Validated properly, not on a single lucky run:
- **5/5 fresh trials** survived at least 12 seconds (previously: 100ms-9s before dying, 0/many survived this long with the stock gadget present in any configuration tried).
- **One extended trial survived 55+ continuous seconds**, idle and stable (252 heartbeats, no crash, no kill) — by far the longest any instrumented session has lasted this entire project.
- The already-proven 42-site kill patch and the `DecryptECC` native hook (both wired in `poll_block.js`) are confirmed firing correctly in every trial (`PATCHED 42/42 kill-signal sites`) — this is the **first time** both defenses have actually gotten a chance to matter, since the process now lives long enough.
- Other "pool-frida"/"gmain"/"gdbus" GLib-internal thread names (which also contain "frida" or are otherwise Frida-associated, baked into the vendored GLib dependency, not patchable without a separate GLib source build) are **still present** and the process survives anyway — strong evidence the detection specifically keys on the exact string `"frida-gadget"` (a well-known, specifically-documented name) rather than a broad "any thread name containing 'frida'" scan. This also finally explains the entire session's `SIGKILL`/`SIGSEGV` saga: it was never about ptrace, RWX memory, sockets, or file I/O — it was a trivial, exact thread-name string match the whole time, just never visible until gadget-mode isolated it from every other variable.

**Not yet reached**: `libecc-encryption.so` hasn't loaded in any trial yet (confirmed by checking every "new anon r-x range" log line's size against the known ~0x47000-byte signature — none match). This is very likely because the repackaged APK is a fresh install with no logged-in account (the original session was lost when the app had to be uninstalled to install the gadget-patched build per user's earlier approval) — the ECIES-encrypted endpoints (`get_push_servers`, `get_care_baby_devices`, etc.) are plausibly gated behind being logged in, consistent with everything learned earlier this project. **The actual remaining step is mundane: log back into the app UI** (it's currently alive and idle, running fine) to trigger real authenticated traffic, not further reverse-engineering or defense-building.

## Root-caused the fault storm: a broken self-fix, not a new detection mechanism (2026-11-21, continued)

## Defeated the full native kill chain (raw syscalls included); found the detection's next fallback is a Java-level self-minimize; solved the gadget's Java.perform limitation via frida-server + frida-compile (2026-11-21, continued)

This entry covers a full session of escalating fixes that took survival at `LoginActivity` from ~400ms to indefinite (modulo one remaining Java-level issue), plus the tooling change needed to finish the job.

### 1. Thread-correlated gating replaces blanket exit()/_exit()/abort() no-ops

The previous session's blanket no-op on `exit`/`_exit`/`abort` stopped the kill but also corrupted the process (confirmed: disabling it reproduced the exact same Binder `"Bad file descriptor"` / IME-focus crash cascade seen before — meaning the no-op itself, not the kill attempt, was the cause, by blocking some *other* legitimate caller's `exit()`/`_exit()`).

Fix: track a `suspiciousThreads` map, populated only when `sendSignal`/`kill`/`tgkill`/`raise` fires with a **real** (non-zero) signal on a given tid. The `exit`/`_exit`/`abort` replacement checks this map and only no-ops on a thread already caught attempting a real kill; every other thread's calls pass through to the real implementation (captured as a `NativeFunction` *before* `Interceptor.replace` patches the export, since reading through the patched address afterward just recurses into our own replacement).

### 2. The detection also uses raw inlined syscalls — confirmed and now blocked

Even with gating, one trial showed `kill`/`_exit` neutered via our libc hooks yet the process still died via a process-wide Binder fd failure the same millisecond — meaning a **raw `svc` instruction bypassing libc** was also in play (consistent with the already-known 42-site payload's habit of inlining syscalls directly).

Fix: dynamically `Stalker.follow(tid, {...})` **only** the specific thread already marked suspicious (never the main thread — full-process/main-thread Stalker was already proven unstable earlier this project), with a `transform` callback that inspects every `svc` instruction's `x8` (syscall number) via a `putCallout`, and redirects `close`(57)/`exit`(93)/`exit_group`(94)/`kill`(129)/`tkill`(130)/`tgkill`(131) to a bogus number.

**Bug found and fixed**: the first version redirected `x8` to `0xffff` (an invalid syscall number), which tripped **Android's own seccomp-bpf filter** (standard on all app processes) and SIGSYS-killed the process (`logcat`: `"exited due to signal 31 (Unknown signal 31)"`). Fixed by redirecting to `getpid` (`x8 = 172` on arm64) instead — a real, always-allowed, harmless syscall. **Confirmed working**: logcat shows `"*** raw syscall kill (nr=129) on stalked tid X BLOCKED (x8 -> getpid)"` and the process survived ~10+ seconds of clean heartbeats with zero crash, the longest clean run of the entire project.

### 3. `close()` on the Binder fd is also part of the kill sequence

Alongside raw syscalls, the detection thread calls libc `close()` repeatedly, including on low fd numbers (confirmed `close(fd=3)`, the Binder driver fd opened once by Zygote) — this is a deliberate "sever IPC" step taken *alongside* the exit attempt, not a side effect of blocking exit. Fixed the same way as exit/_exit/abort: gate `close()` behind the suspicious-thread check (captured original `NativeFunction` before replacing, same recursion pitfall as above).

### 4. New discovery: once every native kill path is blocked, the app falls back to self-minimizing via `startActivity(ACTION_MAIN, CATEGORY_HOME)`

With steps 1-3 in place, the process stops dying outright but still disappears from the foreground ~300ms-10s after `LoginActivity` resumes. `logcat` shows the smoking gun directly:
```
ActivityTaskManager: START u0 {act=android.intent.action.MAIN cat=[android.intent.category.HOME] ... cmp=com.android.launcher3/.uioverrides.QuickstepLauncher} ... from uid 10199 (com.oceanwing.care.cam)
```
i.e. **the app itself calls `startActivity` to launch the home screen**, attributed to its own uid, as a software-level "hide myself" fallback once every lower-level kill mechanism is defeated. Once backgrounded this way, Android's normal cached-process reclaim kills it after its standard ~10s grace window — this part is ordinary OS behavior, not anti-tamper, confirmed by the clean `"has died: prev LAST"` kill reason (no crash signature).

Workaround tried and confirmed effective as a stopgap: `adb shell am force-stop com.android.launcher3` (and the device's fallback HOME handler, `org.localsend.localsend_app`, when launcher3 is unavailable) right as `LoginActivity` comes up — with no valid HOME target to resolve to, the self-minimize intent fails and the activity stays in foreground. Not durable (launcher respawns, intent resolution can fall through to other installed apps), but proves the mechanism and unblocks manual testing in the meantime.

### 5. The real fix needs a Java hook, which `Java.perform()` cannot provide in gadget *script mode*

Blocking the HOME self-minimize properly needs a Java-level hook on `Instrumentation.execStartActivity` (the common dispatch point every `startActivity` overload funnels through), since no native hook distinguishes "this is the app's own home-launch fallback" from any other Binder transaction without fully parsing the Parcel.

**Found a second silent-death bug of the same class as the `send`-reassignment bug from before**: calling `Java.perform(...)` unguarded at the top of the gadget script threw silently and killed the *entire rest of the script* with zero log output (confirmed: two separate pids' logs both stopped dead at exactly `"[poll] script loading"`, the very first line). Deferring it with `setTimeout(fn, 0)` and wrapping in `try/catch` fixed the silent-death problem and surfaced the real underlying error: **`ReferenceError: 'Java' is not defined`**.

Root cause: frida-gadget's **script mode** loads via `dlopen()` extremely early — before the app's main thread can attach to the JVM in a way the bundled Java bridge can use — and, separately, **modern Frida (16+/17.x) no longer exposes `Java` as an automatic global**; it must be explicitly imported (`import Java from 'frida-java-bridge'`) and bundled via `frida-compile`, which our plain-script `poll_block.js` never did.
